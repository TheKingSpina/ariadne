# Mandato WP2 — Esportazione verificabile e ripristino non distruttivo

Data: 2026-11-05. Emesso dall'orchestratore. Nessun commit, nessun push,
nessun container avviato/fermato/ricostruito.

## Contesto

`dashboard/server.py` usa SQLite (`logs`, `events`, `fixtures`, `memories`) con
trigger append-only. Il volume `ariadne-dashboard-data` sopravvive ai riavvii,
ma non è un backup. Il token di scrittura vive in `/data/.write-token` e **non**
deve essere esportato.

## Obiettivo

Creare `dashboard/backup.py`, uno strumento CLI autonomo (solo standard
library) per esportare, verificare e ripristinare l'archivio senza sovrascrivere
silenziosamente dati esistenti.

## Formato di esportazione

Un singolo file JSON con:

```json
{
  "schema": "ariadne-backup/1",
  "created_at": "2026-11-05T...Z",
  "source": "ariadne.sqlite3",
  "data": {
    "logs": [{"id": "...", "version": "2"}],
    "events": [{"log_id": "...", "seq": 0, "line": "..."}],
    "fixtures": [{"log_id": "...", "fixture_id": "...", "binding": {...}}],
    "memories": [{"id": 1, "content": "...", "source": "...", "tags": [...], "created_at": "..."}]
  },
  "integrity": {"algorithm": "sha256", "digest": "<sha256 del JSON canonico di data>"}
}
```

- JSON canonico: `sort_keys=True`, separatori `(",", ":")`, `ensure_ascii=False`.
- `source` è il solo nome del file, non un percorso assoluto.
- Il token non è incluso né letto.
- L'esportazione usa l'API di backup online di SQLite (`sqlite3.Connection.backup`)
  su una copia temporanea, così non legge un DB in scrittura in modo incoerente.
- `verify` ricalcola il digest e rifiuta file alterati o con schema ignoto.

## Comandi

Dalla radice del repository:

```sh
python3 dashboard/backup.py export --database /data/ariadne.sqlite3 --output backup.json
python3 dashboard/backup.py verify --input backup.json
python3 dashboard/backup.py restore --input backup.json --database /data/ariadne.sqlite3 --replace
```

- `export`: crea il file con permessi `0600`; se `--output` esiste, rifiuta
  senza `--force`.
- `verify`: stampa schema, conteggi e digest; esce non zero se non valido.
- `restore`: **prima** valida schema, digest e contenuto; poi costruisce un
  nuovo database in `<database>.restore-tmp`. Se il database di destinazione
  esiste e contiene righe in una qualsiasi tabella, rifiuta senza `--replace`.
  Con `--replace`, copia il database esistente in
  `<database>.pre-restore-<UTC>` (stessa directory) **prima** di sostituirlo.
  Se il destino non esiste, crea la directory padre. Non toccare
  `.write-token`.
- Dopo la ricostruzione, verificare ogni log con `mcp.ariadne_server.tool`
  (`ariadne_verify`, versione e fixture del registro) prima di rendere attivo
  il nuovo database. Se un log non passa, abortire lasciando intatto il
  database esistente.
- `restore` deve essere atomico: il database attivo viene sostituito solo a
  validazione completata. Su errore, rimuovere i file temporanei e non lasciare
  il target in stato parziale.
- Codici di uscita non zero e messaggi su stderr in caso di errore; nessun
  percorso assoluto nei messaggi di successo oltre a quello richiesto.

## Test richiesti

Nuovo `dashboard/test_backup.py` (unittest, eseguibile con
`python3 -m unittest -v dashboard.test_backup`):

- roundtrip export → verify → restore su un DB nuovo: stessi log, eventi,
  fixture e memorie; `Store` riapre e legge;
- digest alterato → `verify` e `restore` falliscono;
- schema sconosciuto → rifiuto;
- destinazione non vuota → rifiuto senza `--replace`;
- `--replace` → crea la copia `<db>.pre-restore-*` e conserva i dati vecchi
  nella copia;
- token escluso dall'export e invariato dopo il restore;
- log non valido (catena rotta) → il restore fallisce e il DB esistente resta
  invariato;
- `--output` esistente → rifiuto senza `--force`.

Aggiornare `dashboard/README.md` con una sezione "Backup e ripristino":
comandi, cosa contiene il file, cosa non contiene (token), limiti (non è prova
di verità o autenticità; il ripristino è locale e offline; il file va protetto
perché contiene memorie e log).
